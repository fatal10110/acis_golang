# Contributing to acis_golang

Thank you for helping. This page explains how to report problems, how to propose changes, and what
a pull request needs before it can be merged.

Everyone taking part is expected to follow the [code of conduct](CODE_OF_CONDUCT.md). To report a
security problem, follow [SECURITY.md](SECURITY.md) instead of opening a public issue.

## How the project works

All code in this repository was generated by AI. Most changes are made by AI coding agents working
from GitHub issues, and reviewed before they are merged. The rules on this page, and in the guides
it links to, apply to every contribution, from a person or from an agent.

Work is tracked in [issues](https://github.com/fatal10110/acis_golang/issues), grouped into
[milestones](https://github.com/fatal10110/acis_golang/milestones).

## Reporting a bug

Search the open issues first. If the problem is new, open an issue and include:

- what you did, step by step, as a player or an operator;
- what you expected, and what happened instead;
- what the aCis Java server does in the same case, if you know. The Go server aims to behave the
  same ([decision 0001](docs/decisions/0001-stay-compatible-with-acis.md));
- the commit or release you ran, and how (Docker or direct);
- relevant log lines, with account names, passwords and IP addresses removed.

Some differences from the Java server are deliberate. They are listed as *parity exceptions* in
[docs/agents/porting-playbook.md](docs/agents/porting-playbook.md#3-check-the-client-visible-surface).
Check that list before you report one.

## Proposing a change

For a small fix, open a pull request directly. For anything larger, such as a new system, a change
in architecture, or a deliberate difference from the Java server, open an issue first, so the
approach can be agreed before work starts.

A change to one of the [architecture decisions](docs/decisions/README.md) needs a new decision record
in the same pull request.

## Making the change

1. Set up your checkout and run the tests: [docs/development.md](docs/development.md).
2. Create a branch from `main`.
3. Make the change. Follow the [code rules](docs/development.md#code-rules) and the
   [style guide](docs/agents/go-style.md).
4. Add or update tests. A new feature gets a behavior test in `tests/<area>/`
   ([test strategy](docs/agents/test-strategy.md)).
5. Update the docs if behavior, config, commands or operations change.
6. Run the checks below.

### Checks before you open a pull request

```bash
make test-race
```

```bash
golangci-lint run ./...
```

Also, when they apply:

- If you changed a packet decoder or framing code, run its fuzz target for at least a minute
  (`make fuzz FUZZ=<Target>`).
- If you changed geodata code or anything the reference tests cover, run those tests locally. CI
  cannot run them ([docs/agents/verification.md](docs/agents/verification.md#datapack-geodata-and-reference-tests)).
- If you changed only documentation, check that every link works.

[docs/agents/verification.md](docs/agents/verification.md) lists the checks for each kind of change.

### Commit messages

Use one line that starts with the area you changed, then a short summary in lower case, then the
issue number:

```text
clan: hand a removal racing a logout to the leaving member (#5549)
fix(skill): save a grown seed effect at its skill level (#5525)
docs: record ten kept-Go parity exceptions (M14)
```

Add a body when the reason for the change is not obvious from the summary.

### Pull requests

- Keep each pull request to one issue or one topic.
- Fill in the pull request template: what changed, why, how you tested it, and which issue it
  closes (`Closes #123`).
- List the checks you ran and their results. Do not claim a check passed if you did not run it, and
  say so if a test was skipped.
- CI must pass. The required check is `go`, which needs the `test`, `lint` and `docker` jobs to pass.
- A reviewer may ask for changes. Answer every review comment, either with a fix or with a reason.

## Questions

Open an issue and describe what you are trying to do. Documentation gaps are bugs too: if something
in the docs was unclear, say so.
